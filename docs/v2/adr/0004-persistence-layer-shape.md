# ADR-0004: Persistence layer — SQLAlchemy 2.x async + separate Pydantic models + Alembic

**Status**: Accepted
**Date locked**: 2026-05-27
**Decision-maker**: John Wolf

## Context

v1 accesses the DB through a single `Postgres` CRUD class with `%s` placeholders and a god-object `StockData` singleton. There is no ORM, no migration framework (schema is append-only via a `schema.py` that runs on startup), and no separation between "the shape stored in the DB" and "the shape exposed to consumers." With an external consumer (Cowork) in v2, leaking internal computation fields (`alert_data` JSONB, `momentum_history`) through the public API would be a real risk.

## Decision

- **SQLAlchemy 2.x async** for DB access. DB models live in `libs/persistence/models/`.
- **Separate Pydantic models** for domain/API shapes in `libs/domain/`. **Repositories convert** between DB models and domain/API models — internal-only fields never cross into the public surface.
- **Alembic migrations** with autogeneration from the SQLAlchemy models. Hypertable creation (TimescaleDB) is raw DDL inside the relevant Alembic revision.
- **Validation at the boundary** — external data is validated/coerced as it enters (generalizing v1's ad-hoc `_num`/`_bigint` pattern; see ADR-0006/0007).

## Consequences

- Clean separation of persistence shape from contract shape; the public API can evolve independently of table layout.
- Async all the way down removes v1's event-loop blocking.
- Principled, reversible migrations replace append-only `schema.py`.
- Cost: two model definitions per entity (DB + domain) and the repository conversion layer — more boilerplate than a single shared model, accepted as the price of not leaking internals to Cowork.
- Autogenerated migrations still need human review (especially around hypertables, which Alembic can't infer).
