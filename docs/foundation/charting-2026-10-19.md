Five audits were run first (inputs, in [audit/](./audit/)):

Headlines: Phase 2 ran 96 days against a 6-8 week appetite with one of ten slices merged and nothing built for the detector; design, not implementation, was the bottleneck (about 86k words of design text against about 4.9k lines of v2 source); the planned single alert class (options flow inferred from 5-minute chain snapshots) cannot report direction and had no predictive evidence.

## Decisions

### Q1 - Who RocketStocks is for, and what it does

Users: John plus a handful of friends in one private Discord server.
Alerts give context that supports intuition-driven, real-money picks.
v2 succeeds if it surfaces stocks John would not otherwise have found that he wants to invest in: price movements that indicate future direction with a stated confidence, and stocks starting to become popular in some circles together with why.

Settled description:

> RocketStocks is a personal trading-research assistant that lives in Discord, where it makes stock research accessible to John and his friends.
> A Data API lets external clients pull the data RocketStocks collects and trusts, so they can produce their own analyses that RocketStocks does not (for example, LLM-assisted report generation).
>
> - **Push - it watches and tells.** Price/volume behavior that has historically preceded a move in one direction, with that pattern's track record; stocks gaining attention in online communities, with why; scheduled digests of notable movers.
> - **Pull - it answers when asked.** Anyone in the server asks for a research-grade read on a stock: the context needed to judge a pick yourself.

Principles:

- **Discord first.** Every feature is designed for Discord. The Data API exposes data, not features.
- **Personal.** Built to John's research standards and workflow; friends get the same output with zero setup; one private server.
- **Research-grade.** See Q2.
- **Advisory.** People decide, with real money; nothing is automated.
- **For fun.** Running cost and operator effort are sized for a hobby.

### Data API guardrails (confirmed)

- Clients are ones John operates (his own tools and LLM sessions). Friends get analyses through Discord only.
- Local network only - no public ingress.
- Read-only, least-privilege database role; one key per client; no scope or rate-limit machinery.
- Derived data first; raw vendor data only to John's own tools.
- One query layer with two thin adapters (bot and API); the bot does not go through the API.
- REST vs MCP shape is a research ticket.

Reason: the strongest argument against non-Discord interfaces is redistribution of vendor data (Schwab revoking API access is fatal to the project) plus the security and contract cost of public exposure on a home-lab VM.
It shapes the API rather than removing it, because John uses it personally.

### Q2 - "Developed with algorithmic trading in mind" = research-grade

- **Trusted signals:** every signal is event-studied against history before it ships; every alert is logged with its signal version; an alert's confidence is the pattern's historical base rate shown in the alert, not a model probability.
- **Trusted data:** validated at the edges, gap-aware (failures recorded, never silently missing), stamped with when it was fetched and how it was adjusted.
- Backtesting strategies and evaluating signals are core v2 scope.
- **Auto-trader infrastructure is a post-v2 follow-up:** replay of every input, point-in-time membership history, latency budgets, extraction seams, broker path.

### Q3 - Map destination

A short, merged v2 foundation plan that leaves no foundational decision open: a charter, an architecture one-pager, vendor choices, keep/cut verdicts on existing v2 code/docs/ADRs (superseded docs archived), and a roadmap to first Discord value with the first slice specced.
Development time is not a planning concern; no appetites or timeboxes.
Kept as scope limits: the deferral test (a question answerable at build time is not a ticket), research summaries of two pages or less, and a finished plan of about 5k words or less.
